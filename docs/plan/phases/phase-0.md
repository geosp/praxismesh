**Phase 0 execution and independent review protocol (planning only; no work has started)**

The *bootstrap prerequisite* in §0 must pass before any Phase 0 session starts. For this phase, use separate, fresh Claude Code sessions with the existing exported specialist skills. **Git and the approved Phase 0 requirements are the common inputs; conversation histories are not.** The master session coordinates handoffs and approval but does not substitute its judgment for an independent reviewer.

**Light-tier application (rev 2.9):** Phase 0 runs under the §7.0 light tier. The independent implementation-review and independent verification steps below run as **one** fresh session that invokes both skills in sequence against the same `code_sha`, recording review findings before verification begins. Record `docs_sha` only if documentation lands in a separate commit; otherwise validate the docs at the PR head. Every other step applies as written.

- [x] **Specification alignment, before design:** Define the Phase 0 scope in an approved OpenSpec specification/change referencing the relevant `PROJECT_PLAN.md` requirements. Record a simple traceability list (requirement -> spec -> acceptance test). Before implementation, check that the master plan and OpenSpec do not contradict each other; resolve any conflict explicitly. Do not let a proposed OpenSpec change silently override the master plan. *(Done 2026-11-11: OpenSpec change `phase-0-local-infrastructure`, four capabilities citing plan sections, `openspec validate --strict` passes; traceability table in the RFC. No conflict with the plan; deviations are recorded in the decision log.)*
- [x] **Skill provenance, before sessions:** Export the existing design-review, implementation-review, and verification skills from the other Claude Code account. Inspect for secrets, absolute paths, external dependencies, and excessive permissions; choose project-level installation where suitable. Commit sanitized skill definitions or pinned, reproducible references to them, recording their versions. Keep private credentials and per-user secrets out of Git. *(Met before Phase 0, confirmed at the Phase 0 close: the skills are committed in `.agents/skills/` and their agents in `.agents/agents/`, versioned in Git; the originals were written by the owner, so there is no external version to pin (issue #1). CI scans every PR for secrets.)*

Implement on a dedicated branch, commit small changes, run the Phase 0 tests and demo, and hand off the exact commit SHA, commands, test output, and demo evidence. No review-session conversation history is needed. *(Done: PR #36 at `075791a`, then fix PRs #38, #40 and #42; evidence in `docs/demos/phase-0.md`.)*
- [x] **Independent implementation review session:** In a new session, supply the approved spec/design and immutable tested implementation `code_sha`, but not prior reviewers' reports, verdicts or implementation-session transcript. Invoke the existing implementation-review skill; independently inspect code, tests, security/secret handling and integrations. Save findings under `docs/reviews/phase-0/implementation-review.md`, with the inspected `code_sha` and blocking issues. Recording the report in Git does not change the source snapshot being reviewed. *(Done in fresh sessions: `075791a` FAIL, `61c40ef` FAIL, `f0337f1` FAIL; every finding fixed or answered in the three response files in `docs/reviews/phase-0/`.)*
- [x] **Independent verification session:** In another fresh session, supply approved requirements/acceptance criteria, environment prerequisites, frozen implementation `code_sha` and the as-built documentation revision `docs_sha`. Do **not** seed the verifier with implementation or reviewer transcripts, earlier verdicts or conclusions. Invoke the verification skill to reproduce tests, Phase 0 live demo (including failure/recovery), and documented as-built claims. Save factual findings under `docs/reviews/phase-0/verification.md` and `docs/demos/phase-0.md`, identifying the tested source and documentation revisions. These evidence files need not contain the SHA of a later commit that incorporates them. *(Done in fresh sessions alongside each review: `075791a`, `61c40ef` and `f0337f1`; every acceptance test and demo step passed each time; the fails were as-built claims and tooling edge cases, all fixed.)*
- [x] **Coordinator approval gate:** The master session checks approved design, independent implementation review, tests, verification, demo and as-built evidence against the recorded `code_sha`/`docs_sha`. It then checks all required status checks on the **actual latest** `head_sha` and confirms that relevant source content matches the reviewed source snapshot. Changes to source require affected code review, tests and documentation checks; docs-only changes require affected doc checks and latest-head CI without automatic repetition of unaffected code checks. Store the final `head_sha` linkage in a separate PR/check/approval record rather than inside a self-referential tracked document. Mark Phase 0 complete only after these conditions pass; otherwise return precise blockers. *(Closed 2026-11-11 by owner decision after PR #42, without a fourth review round, under the §7.1 review-overhead trigger; see the decision log. The final fixes are covered by tests and the required `ci-ok` check, including the `stack` job.)*

**Session handoff contract:** Every handoff names the approved requirements/spec revision, the **relevant** immutable source or documentation revision (`code_sha` and/or `docs_sha`), skill/version used, reproducible commands, artifacts, findings and pass/fail state. The coordinator additionally records final `head_sha` after it exists. Reviewers independently assess approved artifacts, not earlier reviewer conclusions; handoff files are evidence, not a substitute for independent assessment. This process adds no runtime components to Phase 0.
