**Major 1. A task that ends while reconcile runs can be listed as never ended (R17).**
- **Location:** /home/geo/develop/praxismesh/orchestrator/reconcile.py:89-106.
- **Cause:** The list of unended tasks (`ended_at IS NULL`) is read from the snapshot at line 92. Temporal is then asked about each task one at a time, later and outside that snapshot (lines 102-105). `end_task` commits `ended_at` inside an Activity, and only then does the Workflow close.
- **Failure scenario:** Task T is running, so the snapshot holds T with `ended_at` NULL. While reconcile is still asking Temporal about earlier candidates, T's `end_task` commits and its Workflow completes. `status_of(T)` returns `closed`, so T lands in `never_ended` and reconcile exits 1.
- **Where it happens:** Most likely in restore.sh's own report. restore.sh runs `compose start $restart` and then runs reconcile straight away (/home/geo/develop/praxismesh/infra/restore.sh:84-93), so Workflows that were running at backup time resume and finish exactly in this window. The longer the list of unended tasks, the wider the window, because the questions to Temporal are sequential.
- **Why it is Major:** The new runbook text says "A task listed as never ended can be deleted with `request delete --force`". An operator following it would delete a request that actually succeeded. The runbook documents the matching race for dangling references, but not this one.
- **Fix:** For each candidate whose status is not running, read `ended_at` again before listing it.
- **Test that would expose it:** Use a `status_of` that, when asked about task T, first calls `end_task` for T and then returns "closed". Assert that T is not in `never_ended`. The existing `test_a_task_whose_workflow_closed_is_listed_as_never_ended` uses a static FakeTemporal, so it only covers the case with no concurrency.

**Major 2. Backup and restore only stop workers that are in the `running` state (D8: "stops the workers while it dumps ... so no Workflow gets ahead of its rows").**
- **Location:** /home/geo/develop/praxismesh/orchestrator/backup.py:116-118 and 202-206; /home/geo/develop/praxismesh/infra/restore.sh:53-58.
- **Cause:** The list of workers to stop comes from `compose ps --status running`. A worker in Docker's `restarting` state is not `running`, so it is not stopped. Every worker has `restart: unless-stopped`, so it comes back up by itself while the dumps run. The Compose file documents exactly this state for the DSH workers: "until the launcher is up it exits and is restarted" (/home/geo/develop/praxismesh/infra/docker-compose.yml:189). Any worker crash-looping after an OOM or a connection error is in the same state.
- **Failure scenario:** At backup time `worker-dsh-a` is between restarts. Backup stops only the others, dumps `praxismesh`, then `worker-dsh-a` comes up and runs an Activity, so a checkpoint or `end_task` commits and the Workflow advances. `temporal` is then dumped. The restored Temporal history is ahead of the restored rows, which is exactly what D8 says the stop prevents.
- **Fix:** Stop every service in WORKERS unconditionally, and restart only the ones that were running.
- **Tests:** No test exercises a worker that is not running. In /home/geo/develop/praxismesh/tests/integration/test_backup.py, `RecordingCompose` always reports `worker-a` as running. The drill stops real workers, but only `orchestrator`, `worker-a` and `worker-b`, never the DSH pair.
- **Test that would expose it:** A `RecordingCompose` whose `ps` omits `worker-dsh-a` (the restarting case). Assert that `stop` is still issued for it.
