# Impl review, phase 03, round 1: failure lens

Diff `285dd44..89ac455`, files read at `89ac455`. Contract: plan.md (R4, R19, R20, D3, D5, D6, notes.md#rollout) and phases/03-acceptance.md.

## Units examined (awaits and side effects, in order)

1. **`tests/benchmarks/run.py` `main`**: parse args, then `profile_template` (registry load), then the `VLLM_BASE_URL` check, then a tempdir. For a `dsh` profile, `paired_dsh` runs `build_image` (docker build, up to 900 s), then `start_container`: `mkdtemp`, `docker run -d`, and a 30 s poll for the control socket. It then sets `os.environ["DSH_CONTROL"]`. Next, `running_workers` sets the env vars, connects, and builds the orchestrator worker and the template worker; `build_harness` calls `dsh.check()` once (workers/main.py:91-98). For each task, `run_one` runs `setup`, `ensure_bucket`, `prepare_task` (blob puts) and `start_task` (Temporal start). It then awaits `handle.result()` with no timeout, reads the latest checkpoint, unpacks it, runs `task.check`, and runs a DB sum. The row is appended in memory only. After the loop: worker shutdown, then `container.stop()` (docker rm, a docker run that does `rm -rf`, then `rmtree`), then `environment()` (prompt read, `harness_label` parses requirements.txt), then the writes of the `.md`, `.json` and, with `--baseline`, `baseline.json`.
2. **`.github/scripts/check_dsh_licences.py export`**: `docker build`, `docker create`, `docker cp`, `docker rm`, `rmtree(NOTICES)`, then a per-pin `copytree` (it may `SystemExit` midway), then `check()`.
3. **Compose DSH pairs and the runbook switch/revert procedure**: pause, edit, lock, `make workers-up` (rebuilds and recreates every worker-image service and both DSH pairs), update submitters, check. Helpers relied on: `resolve_capabilities` (orchestrator/activities.py:71-90), `Registry.resolve` (registry/loader.py:116-137), `NON_RETRYABLE` includes `CapabilityError` (orchestrator/workflow.py:29-39), `DshRunner.check`/`_verify` (harness_activity/dsh/runner.py:274-301; `unhealthy` is sticky), the activity preflight to `on_unserviceable` (harness_activity/activity.py:226-243), `stop_polling` (workers/main.py:162-167), and launcher `destroy`/`DIRTY`/`reap` (infra/dsh/launcher.py:291-340, `main` reaps at :441).

## Findings

### F1 · Major · tests/benchmarks/run.py:217-233, tests/support/dsh_container.py:875-898 · R19, D3, task 1.1

**One unserviceable DSH container stalls the remaining benchmark tasks until they time out and fail. The benchmark neither recovers nor aborts.**

- **Scenario.** `make benchmark ARGS="--profile dsh"` (the R19 run) is running. During task 3, an attempt's cleanup leaves a process or tree behind, for example a forced stop after a stalled model (R9).
  - The launcher adds the attempt to `DIRTY` (launcher.py:316-321), and every `digests` reply reports it until the launcher restarts.
  - The next preflight sets `DshRunner.unhealthy`, which is sticky (runner.py:276-277, 296-298). The activity calls `on_unserviceable` (activity.py:240-242), and `stop_polling` shuts the in-process worker down (workers/main.py:162-167).
  - The benchmark's container is a bare `docker run -d` with no restart policy (dsh_container.py:880-889), so nothing ever restarts it. `running_workers` starts exactly one template worker on a unique queue prefix (tests/support/workers.py:22-28), so no other worker can take the turn.
  - `run_one` keeps awaiting `handle.result()` with no timeout (run.py:111). Each of tasks 3-10 then waits for its turn's `schedule_to_close` (6 x `turn_timeout`, 60 min for `local-dsh`, notes.md#rollout "Drain") and fails.
- **Wrong outcome.** Up to about 8 hours of wall time. The record says "8 of 10 failed: Regression limit exceeded" for R19, an infrastructure fault attributed to the harness.
- **Contrast with Compose.** Compose has `restart: unless-stopped` and a second pair (`infra/docker-compose.yml` dsh-b/worker-dsh-b), so the same fault leaves `default` served. The benchmark is meant to pair "as Compose pairs `worker-dsh-a` with `dsh-a`" (run.py:356-357), but it does not reproduce that failure behaviour.
- **Fix direction.** Watch `workers.main.UNSERVICEABLE` and abort the run with a clear "infrastructure, not judged" verdict. Alternatively, restart the container and rebuild the worker between tasks.
- **Test that exposes it.** Run the benchmark with `--only` on two tasks against a container whose launcher reports `dirty`. For example, after the first task, `docker exec` into the container and create an empty `/sys/fs/cgroup/attempts/x` with a process in it, or monkeypatch `DshRunner.check` to raise `LauncherUnhealthy` after the first task. Assert the run ends promptly with a non-judged verdict rather than blocking on `handle.result()`.

### Nits

- **N1** · run.py:217-237 · R19/R4 · Rows live only in memory, and `environment()`/`harness_label()` run after the whole loop (run.py:233, 370-379). Any exception in `run_one` outside its `try` (S3, `prepare_task`, `ws.unpack`, `task.check`) or in `harness_label` (`KeyError` if the sdk pin is renamed) discards every finished row of a multi-hour DSH run, and there is no resume. This was already true of the old code, but the DSH run is about 1.9x longer and `harness_label` is a new post-run failure point. Compute `env` before the loop and write rows incrementally.
- **N2** · run.py:236 · R4 · The results key `<date>-<profile>` is not tied to the harness. `docs/benchmarks/2026-11-17-default.json` is the R4 evidence on `openai_agents`. A same-day rerun of plain `make benchmark`, whose `default` is now DSH, overwrites it with a DSH run. A `--only` run without `--out` likewise overwrites the full result and is judged against the 10-task baseline (run.py:445, 226: "Regression limit exceeded"). It is recoverable from git, so it is a Nit.
- **N3** · run.py:239-245 · R4 · `--baseline` writes `baseline.json` for any profile, with no harness check. `make benchmark ARGS="--baseline"` now silently replaces the plan's "10/10, openai-agents" baseline with a DSH one, and R4 and R19 are then judged against it.
- **N4** · dsh_container.py:877-889 · task 1.1 · If `docker run` fails (`check=True` raises), the `mkdtemp` attempt dir is leaked. If the benchmark is SIGKILLed, the `dsh-test-*` container (with SYS_ADMIN and a host bind mount) keeps running with no label for later reaping. This is test tooling, so a Nit.
- **N5** · run.py:362-366 · task 1.1 · `paired_dsh` overwrites and then pops a pre-existing `DSH_CONTROL` instead of restoring it. This matters only if a caller had set it.
- **N6** · check_dsh_licences.py:82-91 · R20 · `export` deletes `docs/licences/dsh/` before checking that every pin has `dist-info/licenses` in the image. A missing one exits midway and leaves a partly written notices tree in the worktree (recoverable from git). Validate all pins first, then replace.
- **N7** · runbook.md "Switch" step 1 · D5, notes.md#rollout · "Pause submissions" does not cover a workflow already started whose `resolve_capabilities` has not run yet, for example while the orchestrator is being recreated in step 4. Such a task carries `template=local-dsh` (submit.py:47). The new registry rejects it (loader.py:123-128), with `CapabilityError` non-retryable (workflow.py:29-39), so the workflow fails before `record_task`. The window is narrow, so a Nit. The runbook could say to wait until submitted tasks show a task row before restarting.
- **N8** · runbook.md "Causes and fixes / Dirty container" · R10 · The runbook says "its attempt volume is tmpfs, so nothing survives the restart". The volume is shared with the still-running worker, which keeps the mount, so its contents survive a restart of only `dsh-a`. The fix works anyway, because the launcher reaps every leftover cgroup and tree at start (launcher.py:329-340, 441). The stated reason is wrong, so a Nit.
- **N9** · infra/demo/worker-loss.sh:20, Makefile `demo-worker-loss` · task 2.1 · The script submits without `--profile` (cli default `default`), so this Phase 1 `openai_agents` demo now silently runs on DSH. Its closing hint `docker start $container` restarts only the worker, not a DSH container left dirty. Task 2.1's list of repointed targets did not include it, so the omission is consistent with the plan; it is still a behaviour change.
- **N10** · Makefile:125-127 · task 2.1 · `make workers-up` now also requires the DSH pairs (SYS_ADMIN, private cgroupns, AppArmor unconfined) to become healthy within 300 s. On a host that cannot run them, the command fails partway, with the orchestrator and `openai` workers up, and the runbook's switch and revert step 4 depends on it.
- **N11** · docker-compose.yml dsh-b `depends_on: dsh-a` · D3 · The dependency exists only so the image gets built, but it couples the pairs: `up dsh-b worker-dsh-b` also starts `dsh-a`. This is harmless today.
- **N12** · phases/03-acceptance.md tasks 1.1, 2.1, 2.2 · The diff records no evidence for their verification steps: the per-profile smoke runs, a `default` task on DSH next to an `openai` task, or the revert walkthrough in which a DSH task started before the revert finishes on DSH. There is no `docs/demos/*-03` file. I could not verify these within this review's scope.

## Checked, no finding

- The licence check (R20) is filesystem-only and idempotent. It handles hash continuation lines and normalised names, flags stale directories, and its tests cover a removed notice, an empty directory and an unpinned directory.
- A profile switch cannot move a running task: `TaskStart.template` is fixed at submit, and later activities look up templates, not profiles (activity.py:215, 358, 428; activities.py:53).
- Overlapping benchmark runs use unique queue prefixes, container names and attempt dirs. They share only the N2 results key.
- `paired_dsh` stops the container after the workers have shut down, so on Ctrl-C no attempt is cut off by container removal while its worker still polls.
