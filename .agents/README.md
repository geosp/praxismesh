# `.agents/`: the one real copy of agent skills and agent definitions

This repository is used from several coding harnesses. Each harness looks for skills and agents in a different place, so everything is written **once** here and exposed to each tool by a symlink (skills) or a generator (agents).

```
.agents/
├── skills/<name>/SKILL.md   # skills (Agent Skills format), the real copy
├── agents/<name>.md         # agent definitions, the real copy
├── templates/               # copy-me templates (not scanned by any tool)
└── sync_agents.py           # generates per-harness agent files

.claude/skills  -> ../.agents/skills   (symlink; also read by GitHub Copilot)
.claude/agents/   # generated, Claude Code subagents
.github/agents/   # generated, GitHub Copilot custom agents (*.agent.md)
.codex/agents/    # generated, Codex CLI custom agents (*.toml)
```

## Where each harness looks

| | Claude Code | GitHub Copilot | Codex CLI |
|---|---|---|---|
| Instructions | `CLAUDE.md` → `@AGENTS.md` | `AGENTS.md` | `AGENTS.md` |
| Skills | `.claude/skills/` (symlink) | `.claude/skills/` (symlink) | `.agents/skills/` (native) |
| Agents | `.claude/agents/*.md` | `.github/agents/*.agent.md` | `.codex/agents/*.toml` |

These paths were checked against vendor docs and secondary sources on 2026-11-10. Re-verify them when a harness is upgraded; the conventions are still moving. There is deliberately **no** `.github/skills` link, because Copilot also reads `.claude/skills` and would list every skill twice.

## Skill naming convention

Name every skill `<domain>-<capability>`:

- Lowercase letters, digits and single hyphens; at most 64 characters; no leading or trailing hyphen. The folder name must equal `name:` in `SKILL.md`. Do not use the words `claude` or `anthropic`, which Claude Code reserves.
- **Domain** is a prefix from the table below, so related skills sort together. To add a new domain, add a row here first.
- **Capability** is a short noun or verb phrase for the job. Avoid generic names such as `helper` or `utils`, and do not include version numbers.

| Domain | For | Examples |
|---|---|---|
| `github-` | GitHub issues, pull requests, CI, releases | `github-pr`, `github-issue` |
| `plan-` | working with `PROJECT_PLAN.md` and `docs/plan/` | `plan-context` |
| `spec-` | OpenSpec changes and specs | `spec-change` |
| `review-` | independent reviews | `review-design`, `review-implementation` |
| `verify-` | independent verification | `verify-phase` |
| `docs-` | RFCs, ADRs, as-built documentation | `docs-as-built` |
| `dev-` | local development workflows | `dev-compose-up` |

**Exempt:** skills generated by tools (for example OpenSpec's `openspec-*`) and external specialist skills, which keep their upstream names (plan §0.3). Record any mapping in the decision log. Skills imported from other projects are renamed to this convention when they are adapted (e.g. `pr` became `github-pr`).

## Adding a skill

1. `cp -r .agents/templates/skill .agents/skills/<domain>-<capability>`. The folder name must equal `name:` in `SKILL.md` (see the naming convention above).
2. Edit `SKILL.md`. The `description` decides when an agent loads the skill, so say what the skill does **and** when to use it.
3. Put optional helpers in `scripts/`, `references/` or `assets/` inside the skill folder.
4. Use only the portable frontmatter fields (`name`, `description`, and optionally `license`, `compatibility`, `metadata`) unless you accept that other harnesses will ignore the rest.

No sync step is needed: all three harnesses see the new folder immediately.

**Review and verification skills:** `review-design` and `review-implementation` are project-owned adaptations of skills the repository owner wrote for another of their own projects, and `verify-phase` was written for this project. There is no third-party source or license: all three are part of this repository under its Apache-2.0 license (issue #1). The owner chose adaptation over plan §0.3's "use the original, pinned" rule; see [decision-log.md](../docs/plan/decision-log.md). Change them like any other project file, through a reviewed pull request.

**Per-harness enforcement of session roles** (see [docs/reviews/README.md](../docs/reviews/README.md#session-roles-and-permissions)):

- **Claude Code:** project permission rules in `.claude/settings.json` deny pushes to `main`, force-pushes, repository-setting changes and any writing `gh api` call, and ask before `gh pr merge`; they also bind subagents. Agent tool lists add per-role limits.
- **Codex CLI:** reviewer agents run with `sandbox_mode: read-only`, the verifier with `workspace-write`; Codex enforces these. It does not read `.claude/settings.json`.
- **GitHub Copilot:** limits come from each agent's `tools` list and instructions only; it does not read `.claude/settings.json` and has no sandbox mode here.
- **All tools:** ruleset `protect-main` on GitHub is the one control every session is subject to.

## Adding an agent

1. `cp .agents/templates/agent.md .agents/agents/<agent-name>.md` and edit it. The format is in [agents/README.md](agents/README.md).
2. Run `uv run .agents/sync_agents.py`.
3. Commit the source file **and** the generated files.

`uv run .agents/sync_agents.py --check` exits non-zero when the generated files are stale. Use it in CI.

## Notes

- **Symlinks:** git stores `.claude/skills` as a symlink. Linux and macOS work as is. On Windows, enable Developer Mode and `git config core.symlinks true` before cloning.
- **OpenSpec:** installed with `openspec init --tools agents` (shared `.agents/skills` target). The `openspec-*` skills are generated; refresh them with `openspec update`, never by hand. See [skills/README.md](skills/README.md#openspec-skills-generated) for why only the `agents` target is used.
